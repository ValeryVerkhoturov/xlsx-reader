# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

This is a Go module (`module github.com/yurij-lyubskij/xlsx-reader`, Go 1.24.5) with no external dependencies at all — stdlib only, in both the library and its tests. `go.mod` declares no `require`/`replace` entries. The importable package is `package xlsx`, so callers write `xlsx.OpenReader(...)`.

- Build: `go build ./...`
- Vet: `go vet ./...`
- Test: `go test ./...` (verbose: `go test ./... -v`; single test: `go test ./... -run TestName`)
- View docs: `go doc .` / `go doc . OpenReader`
- Regenerate the real-world (LibreOffice-produced, non-self-produced) `.xlsx` fixtures under `testdata/`: `sh testdata/generate.sh` (requires `soffice` on `PATH`; only needed if those fixtures need to change — they're checked in, so this isn't part of the normal test loop)

See `README.md` for the library's public-facing usage docs and design notes.

## Architecture

- **Root package `xlsx`** (`reader.go`, `zip_stream.go`, `workbook_meta.go`, `styles_meta.go`, `numfmt.go`, plus `reader_test.go`/`reader_format_test.go`/`zip_stream_test.go`/`styles_meta_test.go`/`numfmt_test.go`): the library. It exposes `OpenReader(r io.Reader, opts ...ReaderOption) (*Reader, error)`, which reads any `.xlsx` workbook through a forward-only, constant-memory `Reader`/`Sheet`/`RowIterator` API, with basic number/date formatting controlled by the `RawCellValue` option.

### How the general reader works

`OpenReader` reads any `.xlsx` while never buffering more than one row and never seeking, so its input need only be an `io.Reader`. The two obstacles a general reader normally has to solve — the ZIP central directory sitting at the end of the file, and a shared-strings table that can legally appear anywhere — are sidestepped rather than solved: shared strings are rejected (lazily, per-cell, not by prescanning for `xl/sharedStrings.xml`), and the central directory is never read.

- **`zip_stream.go`** (`zipWalker`, `zipEntry`): a general forward-only ZIP entry reader. It accepts both of ZIP's local-entry encodings (sizes known up front in the local header — what real writers like Excel/LibreOffice actually produce — or deferred to a trailing data descriptor, general-purpose bit 3, when the writer can't seek back to patch the header, as `archive/zip.Writer` never can) and both stored and DEFLATE compression. The data descriptor's optional 4-byte signature is *detected*, not required, by peeking whether the first 4 trailer bytes equal the signature — real-world writers disagree on including it. `zipEntry.finish` drains any data the caller left unread and validates the entry's CRC-32 either way.
  - **Zip64**: a local header whose 32-bit compressed/uncompressed size is the `zip32SizeSentinel` (`0xFFFFFFFF`) is resolved against a Zip64 extended-information record (`zip64ExtraID`, `parseZip64Extra`) in the entry's own extra field — uncompressed size then compressed size, only whichever was actually flagged, matching Go's own `archive/zip` reader exactly (verified against its source). Unambiguous for the common case (Excel, LibreOffice, any seekable-destination writer). For a *streamed* entry, the trailing data descriptor also widens to 8-byte size fields when Zip64 is signaled this way, or when a Zip64 record is present at all (even an empty placeholder some writers use before real sizes are known) — but `archive/zip.Writer` itself can stream a Zip64 entry to a non-seekable `io.Writer` without ever signaling it in the local header at all (confirmed by reading `writer.go`'s `writeDataDescriptor`: "too late anyway" to patch the header by then). That case is genuinely undetectable forward-only: the misread entry's own CRC-32 still checks out (CRC is always the descriptor's first field, unaffected by the size fields' width), so it silently leaves leftover trailer bytes that swallow whatever entry follows — `next` reports "no more entries" rather than erroring. Documented in `next`'s doc comment and pinned by `TestZipWalker_Zip64Streaming_UnsignaledAmbiguityTruncatesArchive`, not hidden or "fixed" with a guess.
- **`workbook_meta.go`**: parses `_rels/.rels` (to find the workbook part's path, defaulting to the near-universal `xl/workbook.xml` until/unless resolved), the workbook part itself (its `<sheets>` list: name + relationship id, in tab order), and the workbook part's own `.rels` file (relationship id → worksheet part path). All three are small and read fully into memory (bounded by sheet count, not data).
- **`reader.go`** (`Reader`, `Sheet`, `RowIterator`, `RawCellValue`): `Reader.NextSheet` drives a `zipWalker` forward, routing each entry by name — root rels, the workbook part, its rels, `xl/styles.xml` (conventional path only, `defaultStylesPath` — unlike the workbook part there's no rels-based resolution, since a style lookup is inherently best-effort anyway), anything matching `looksLikeWorksheetPart` (a direct `xl/worksheets/*.xml` child; detection depends only on naming convention, not on the rels having been parsed yet, since worksheets can be — and with real writers, sometimes are — encountered before that metadata), or else discarded. A worksheet's `Sheet.Name`/`Index` come from the workbook metadata when it's already been resolved by the time that worksheet is reached (`Reader.resolveSheet`); otherwise they fall back to a name/index derived from the archive itself (`fallbackSheetName`, `sheetsSeen`) — real workbooks conventionally write `xl/workbook.xml` before the worksheet parts, but nothing mandates it — a writer that can't seek back to finish `xl/workbook.xml` until every sheet has been streamed out will do the opposite, which is what `TestReader_FallbackSheetNaming`'s hand-built fixture exercises. Each `Sheet` also gets a `*formatContext` snapshotted from whatever styles/`date1904` state has been parsed so far (same graceful, not-retroactive, degrade-to-raw posture as sheet-name fallback if `xl/styles.xml` shows up later). `RowIterator.Next` decodes one `<row>` at a time via `xml.Decoder` into `generalWorksheetCell` (including the cell's `s` style-index attribute) and `buildRow`, gap-filling columns from each cell's `r` attribute (`parseCellColumn`) rather than assuming one `<c>` per column — real workbooks write sparse rows, omitting empty cells entirely. `generalCellText` converts a cell to text, preferring a cached `<v>` when present and falling back to `"=" + F` only when a formula has no cached value; a `t="s"` cell returns an error naming shared strings specifically. Numeric cells (`t=""`/`"n"`) route through `formatContext.formatCellValue` (see `numfmt.go`) instead of always staying raw.
- **`styles_meta.go`**: parses the styles part (`parseStyles`) into `numFmts` (custom `numFmtId` → `formatCode`, from `<numFmts>`) and `cellXfs` (style index → `numFmtId`, from `<cellXfs><xf>`; an `<xf>` with no `numFmtId` attribute defaults to 0/General, matching the XML decoder's zero value). Small, read fully into memory (bounded by style count).
- **`numfmt.go`**: the "basic" number/date formatting engine `RawCellValue` controls. `formatContext.formatCellValue` resolves a cell's style index to a `numFmtId` via `cellXfs`, then tries `formatBuiltin` — a fixed switch over ECMA-376 built-in ids 1-4/9-10 (plain/grouped numbers and percentages, via `formatFixedGrouped`/`groupThousands`, since `strconv`/`fmt` don't do thousands-grouping) and 14-22/45-47 (the standard date/time formats, rendered via `time.Format` layouts for date-bearing ones through `dateFromSerial`, or directly from the fractional/total-seconds part via `timeOfDayFromSerial`/`elapsedHMS` for pure time-of-day and elapsed-duration ones — id 46 `[h]:mm:ss` specifically needs `elapsedHMS`'s un-wrapped hours, not a 24h-wrapping `time.Time`) — then, for a custom id (`numFmtId >= 164`) with no built-in match, `translateCustomDateCode`. That function tokenizes the custom `formatCode` (quoted literals, `\`-escaped chars, runs of `y`/`m`/`d`/`h`/`s`, `AM/PM`) into typed `dateToken`s and aborts (falls back to raw, never guesses) on brackets, semicolons, numeric-format symbols, or any run length it doesn't recognize; `disambiguateMinutes` reclassifies a `tokMonthNum` to `tokMinute` when it's nearest an `h` token before it or an `s` token after it (skipping literals), matching Excel's real `m`/`mm` rule. `renderDateTokens` then executes each token directly against a `time.Time` rather than building one composite `time.Format` layout string, so literal text can never collide with Go's reference-time substrings. `dateFromSerial` uses the classic epoch trick (1899-12-30, or 1904-01-01 for `date1904` workbooks) — correct for every real date from 1900-03-01 onward; serials in Jan/Feb 1900 are a documented, accepted inconsistency (see the test asserting this), not a bug to fix.
- **`testdata/libreoffice_mixed.xlsx`, `testdata/libreoffice_numeric.xlsx`, `testdata/libreoffice_dates.xlsx`**: real, non-self-produced fixtures generated via `soffice --headless` (see `testdata/generate.sh`), used by `reader_test.go`/`reader_format_test.go` to exercise actual Excel/LibreOffice conventions this package doesn't control — real shared-strings usage and rejection of it, real sparse rows, workbook.xml preceding the worksheets, and (`libreoffice_dates.xlsx`) LibreOffice auto-detecting ISO-looking CSV values as dates and assigning a *custom* numFmt with backslash-escaped literal hyphens (`formatCode="yyyy\-mm\-dd"`) rather than one of the built-in date ids — real-world confirmation that the custom-code translator's escape handling isn't just a hypothetical case.
